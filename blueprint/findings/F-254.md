# F-254 - `changePassword` holds a pool connection and the user's row lock across two scrypt runs

**Found:** 2026-10-05 by review (item 15e1; scope: current; lens: every lens; reviewer subagent)
**Why it matters:** The pool is `max: 5` (`app/lib/db.server.ts:5`) and `passwordCheckSlots` allows 2, so two saves can pin 40% of the pool, shared with the public site, for ~0.9 s each; measured p95 is 861 ms against the 1 s *Admin saves* bar. Also differs from the spec's `newHash` signature; `completeReset` hashes outside its transaction.
**Suggested fix:** Verify and hash outside the transaction (still inside the slot), then compare-and-swap: `update users ... where id = $id and password_hash = $oldHash returning token_version`; zero rows answers as a wrong password.
