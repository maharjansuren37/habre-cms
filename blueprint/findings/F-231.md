# F-231 - Signup's concurrent-signup test can take both password slots and make another worker's login answer 503

**Found:** 2026-10-04 by build (autopilot, item 15b step 10), on the full local browser run
**Why it matters:** Signup shares login's two password-hash slots (`passwordCheckSlots`, spec Decisions). `e2e/signup.spec.ts`'s "two signups at once for one address" posts two signups together, holding both slots, while the second Playwright worker (`workers: 2`) may be logging in. That login answers 503 (`login_rate_limited` scope `server` in the server log), and the test waiting for `/admin/posts` times out. Seen once in two full runs (`e2e/site-navigation.spec.ts:38` failed; it passes alone, and the second full run passed 308/308). Before 15b two workers could never hold more than two password checks at once, so the suite never hit this. CI's `e2e` job runs the same suite and can go red at random. Production behaviour is as specified: a burst of signups can briefly make a login answer "busy".
**Suggested fix:** a test-only change. Either have the race test take its two slots when no other worker is logging in - run `signup.spec.ts` in its own Playwright project that depends on the main one - or let the shared `logIn` helper retry once on the 503 "busy" answer, which the app tells people to do. Owner's choice; not built in 15b because the spec does not decide it.
