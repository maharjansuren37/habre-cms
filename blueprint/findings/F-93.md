# F-93 - The settings form silently shows and re-saves stale defaults if `useRouteLoaderData`'s hardcoded route id ever stops matching

**File:** app/features/settings/settings.tsx:59-60
**Found:** 2026-09-23 by review (scope: current, item 7a; lens: quality) - found while re-examining F-91's repair
**Why it matters:** F-91's fix reads the admin-shell layout's already-fetched settings via `useRouteLoaderData<typeof adminLayoutLoader>("features/admin-shell/layout")`, falling back to `{ siteTitle: "Habre CMS", logoMediaId: null, logoUrl: null }` when that lookup returns `undefined` - noted at the time as "practically unreachable." Confirmed live what actually happens if it *is* reached (temporarily pointing the hook at a wrong id, standing in for a future rename of `admin-shell/layout.tsx`): the form silently renders the fallback's stale defaults instead of an error - a real custom title ("Precious Custom Title", saved moments earlier) simply does not appear, and the field shows "Habre CMS" instead, with no visual or console indication anything is wrong. Following through, submitting Save with the field untouched **overwrote the real custom title back to "Habre CMS"** in the database, with the ordinary "Settings updated." success banner - no error, no confirmation, silent data loss. This is `fundamentals.md`'s Errors section by name: "A default value substituted for a failed call hides the failure until it matters." **Not reachable today** - the id string is currently correct, and this needs a future code change (renaming or moving the layout file) to trigger - but nothing in the test suite would catch that rename: none of `e2e/manage-settings.spec.ts`'s five tests exercise a second read of already-set values through this exact path, only a fresh save. F-91's own suggested-fix text already named this coupling as a tradeoff ("or leave as is if the duplication is judged not worth the coupling to the parent route's id"); this finding is the concrete shape of what "not worth it" would look like if triggered.
**Suggested fix:** Smallest change: assert instead of silently falling back - throw (a 500 is honest; a silent revert is not) when `useRouteLoaderData` returns `undefined` for this id, so a future rename fails loudly in `verify`/CI rather than quietly shipping a data-loss path. Alternatively, add one e2e test that changes the title, then re-opens `/admin/settings` and asserts the field shows the real value (not the seeded default) - it would not catch a rename today, but it would at least prove the wiring once, and regress if the id ever silently diverges from what the route file is actually named.

**Resolution:** Fixed in tidy-findings Step 3 (2026-10-02, autopilot): Settings throws when the admin-shell layout data is missing instead of falling back to defaults. No test (spec names none); checked by reading and the settings e2e specs passing. Review 2026-10-02: repaired; stays fixed (autopilot never closes its own repairs).
