# F-243 - A reset completing at the same moment as a new link request can deadlock, and one side answers 500

**Found:** 2026-10-04 by review (independent `reviewer` agent; scope: current, item 15c, main..083986a; lens: all)
**Why it matters:** `completeReset` locks the token row, then the `users` row; `issueResetToken` locks the user (`for update`), then updates that user's reset tokens. A submit of link A and a forgot-password request for the same email inside the same few milliseconds wait on each other; PostgreSQL aborts one with 40P01 and that request answers 500. The rollback leaves the link unused and the slot is released in `finally`, so a retry works. Traced from the lock order, not reproduced.
**Suggested fix:** Take the user lock first in `completeReset` (read `user_id` for the token hash unlocked, `select ... from users where id = ... for update`, then the guarded token update unchanged), or treat 40P01 as a refusal.
**Resolution:** Fixed by build, 2026-10-04: `completeReset` now reads the token's `user_id` unlocked, locks the user `for update` (confirmed, active membership) before touching any token, then runs the guarded token update - the same user-then-tokens order as `issueResetToken`. No test can force the interleaving; `e2e/password-reset.spec.ts` 17 passed after the change. Left `fixed` for `review` to close on reading.
