# F-96 - `navigation` is trusted as `NavItem[]` on read with no format guard, unlike `blocks` - a malformed value would 500 the one page that could fix it

**File:** app/features/settings/settings.server.ts:19-32 (`getSiteSettings`); app/features/settings/navigation-form-input.ts:11-17 (`navItemsToDraftRows`); app/features/public-site/layout.tsx:16-23 (`resolveNavigation`)
**Found:** 2026-09-23 by review (scope: changed, item 7b; lens: quality) - the crash was reproduced directly (a malformed value written straight to the column, bypassing the app), not observed through the product's own request surface
**Why it matters:** `getSiteSettings` reads the `navigation` column and returns it typed as `NavItem[]` with nothing checking that the value actually has that shape - `sql<{ ...; navigation: NavItem[] }[]>` is a type assertion, not a runtime check. `navItemsToDraftRows` and `resolveNavigation` then call `.map`/`.flatMap` on it directly. Reproduced: writing a value to the column that is valid jsonb but not an array (a jsonb *string*, the easiest way to get here being a double-`JSON.stringify` mistake in whatever writes it next) makes `/admin/settings` throw `TypeError: items.map is not a function` in `navItemsToDraftRows` and answer 500 - and because that is the one screen that could fix `navigation`, there is no self-service recovery, only a direct database edit. `entries.server.ts` already has a guard for exactly this class of problem on its own JSON column: `blocks_format` is checked on write and on read (D31, `assertKnownFormat`), specifically because trusting stored JSON blindly was judged risky enough to need an explicit marker. `navigation` has no equivalent. **Not reachable today** through the app's own request surface - `updateNavigation` is the only writer and it always validates through `navigationSchema` before writing (`draftRowsToNavItems`) - so this is a latent gap rather than a live bug: it would need a future writer, a migration, or a manual database edit to trigger. P3 to match how this project has scored a currently-unreachable but real defect before (F-19's undocumented migration policy, similarly a design gap with no current live impact).
**Suggested fix:** The cheapest guard: `z.array(navItemSchema).catch([])` (or a `safeParse` with the same fallback) on the way out of `getSiteSettings`, so a malformed value degrades to an empty menu instead of a 500 - matching D61's own "degrade silently" precedent for this table rather than inventing a new failure mode. A stricter option, matching `blocks_format`'s own choice to fail loudly instead: throw from `getSiteSettings` with a message naming the row, so the failure is visible in the logs rather than silently downgrading a real menu to empty.
**Resolution:** Fixed in tidy-findings Step 3 (2026-10-02, autopilot): getSiteSettings parses navigation with parseStoredNavigation; malformed logs once, reads as []. Unit tests in navigation-input.test.ts red against a stub, green after. Review 2026-10-02: repaired; stays fixed (autopilot never closes its own repairs).
