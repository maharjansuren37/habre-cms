# F-218 - `sites.spec.ts` writes site 1's shared settings row, so specs running alongside can fail

**Found:** 2026-10-04 by review (scope: current; reviewer subagent, item 15a); lens: tests
**Why it matters:** With `workers: 2`, it renames site 1 and `resetSiteSettings()` clears its home page and menu while `public-site`, `smoke` and `home-page` specs assert the default title or a chosen home page; `manage-settings` can also rename site 1 between its own reads. Widens F-103.
**Suggested fix:** Run the settings checks against a third site from `createSite` (site 2 never sees site 3's title; saving site 2 leaves site 3's alone) and drop `resetSiteSettings()` from that `afterEach`.
**Resolution:** fixed by build, 2026-10-04 - the "media and settings belong to one site" settings checks use a third site from `createSite` (deleted in `afterEach`) instead of site 1, and `resetSiteSettings()` is gone from `sites.spec.ts`; `grep -nE "resetSiteSettings|update site_settings" e2e/sites.spec.ts` finds nothing. The two tests were seen red with `settings.server.ts` mutated to read and write the newest site ("Expected: media-…, Received: other-…"; site 3 renamed), green restored. Full `npm run test:e2e` 285 passed. Left `fixed`, not closed: the race itself cannot be reproduced on demand, so no test was seen failing for the reason the finding describes - `review` closes it.
