# F-269 - A client-sent `Forwarded: host=` header may override the pinned `X-Forwarded-Host`, and the host now picks the site and the platform

**Found:** 2026-10-06 by review (scope: current, item 16a; every lens; reviewer subagent)
**Why it matters:** `@remix-run/node-fetch-server` reads RFC 7239 `Forwarded` before `X-Forwarded-Host`; the Caddy file pins X-Forwarded-Host/-Proto (D96, F-22) but not `Forwarded`. Since 16a the host decides platform vs site and which site. No exploit found (host-only cookies, CORS preflight, no shared cache) - unverified whether Caddy passes it through.
**Suggested fix:** In item 16b's Caddy file add `header_up -Forwarded` to every `reverse_proxy`; send `Forwarded: host=app.<platform>` to a site host once and confirm no effect.
**Resolution:** fixed by build (item 16b, Step 4, autopilot, 2026-10-06). `header_up -Forwarded` in the shared `habre_cms_proxy` snippet of `deploy/caddy/habre-cms.caddy`, so every `reverse_proxy` removes it (adapted JSON: all three delete `Forwarded`). Live through a local Caddy 2.11.4 (Docker, `tls internal`) in front of `npm start`: `surenmaharjan.sites.test/` with `Forwarded: host=app.habre.test;proto=https` answers 200 with site 1's page; `app.habre.test/` with `Forwarded: host=nobody.sites.test` answers 302 to `/admin`. With the line removed from the test copy the same two requests answered 302 (served as the platform) and 404 (served as an unknown site) - the defect was real, not only theoretical. Restored, 200 again. Not closed: autopilot never closes its own repairs.
